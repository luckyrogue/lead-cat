# Design — Meetings backend, increment 1

**Date:** 2026-05-30
**Status:** Approved (brainstorm)
**Scope:** First vertical slice of the Google Meet meetings feature (backend). Full product spec (ТЗ): [../../NEW-FEATURES.md](../../NEW-FEATURES.md). Feature summary: [../../MEETINGS.md](../../MEETINGS.md).

## Context & decisions

The meetings feature is large (registration, meeting CRUD, Google Calendar integration, employee directory, recurrence, conflict detection, free-slot checker, notifications). It is built incrementally. Key decisions from brainstorm:

- **Channel: both.** Long term — Telegram bot (registration §3, notifications §5) + Telegram Mini App (rich UI). **This increment serves the Mini App via REST**; bot flows are deferred. Bot and REST will share one domain/application layer.
- **Tenancy: within workspace.** Meetings reuse the existing multi-tenant `workspaces` model, ACL (`RequireWorkspaceAccess`), existing `users`, and Telegram linking. Per-workspace Google config (mirrors the existing encrypted per-workspace VCS token pattern).
- **Architecture: ports + adapters (approach A).** Google Calendar access sits behind a `CalendarService` port owned by `application`; adapters live in `infrastructure/calendar/` (`stub` now, `google` later). Matches the Clean Architecture / DI principles in `AGENTS.md`.
- **First increment:** meeting CRUD over REST + Google port with a **stub** (no real Google credentials yet).

## Module layout (clean architecture)

```
domain/meeting/          meeting.go (entity, enums), naming.go (name standard), validate.go
application/             meeting_service.go (Create/List/Get/Delete) + CalendarService port
infrastructure/
  calendar/stub/         stub.go (fake eventID + meet link)        <- real google/ in a later increment
  persistence/postgres/  meeting_repo.go, employee_repo.go, models (Meeting, Employee, Participant)
delivery/http/handlers/  meetings.go (+ routes under workspace)
```

The `CalendarService` interface is defined by `application` (the port); concrete adapters in `infrastructure/calendar/` implement it. Wired in `cmd/server`.

## Data model (new goose migration, all workspace-scoped)

**employees**

- `id uuid pk`, `workspace_id uuid fk`, `full_name text`, `email text`, `dept text`, `has_telegram bool`, `created_at timestamptz`
- unique `(workspace_id, email)`

**meetings**

- `id uuid pk`, `workspace_id uuid fk`, `organizer_user_id uuid fk`
- `dept text`, `type text`, `host text`
- `starts_at timestamptz`, `ends_at timestamptz`
- `recurrence text` (enum: `once|daily|weekly|biweekly|monthly|...`), `recurrence_until date null`
- `name text` (auto-generated), `description text`
- `google_event_id text`, `meet_link text`
- `status text` (`scheduled|cancelled`)
- `created_at timestamptz`, `updated_at timestamptz`

**meeting_participants**

- `meeting_id uuid fk`, `employee_id uuid null fk`, `email text` (event guests)

Times stored as `timestamptz` (UTC); display timezone Almaty (UTC+5) per ТЗ.

## Google port + stub

```go
// application
type CalendarEvent struct {
    Title, Description string
    Start, End         time.Time
    AttendeeEmails     []string
}
type CalendarResult struct {
    EventID  string
    MeetLink string
}
type CalendarService interface {
    CreateEvent(ctx context.Context, e CalendarEvent) (CalendarResult, error)
    DeleteEvent(ctx context.Context, eventID string) error
}
```

Stub (`infrastructure/calendar/stub`): returns `EventID = uuid`, `MeetLink = https://meet.google.com/stub-<short>`. `DeleteEvent` is a no-op success.

## REST API (existing JWT + `RequireWorkspaceAccess`)

- `POST /api/workspaces/:id/meetings` — create. Body: `dept, type, host, date, start, end, recurrence, participants[] (employee_id or email), description`. Flow: validate → generate name → `CalendarService.CreateEvent` → persist meeting + participants → return meeting.
- `GET /api/workspaces/:id/meetings` — list. Returns own meetings; **all** meetings if the member's role is admin (matrix §2).
- `GET /api/workspaces/:id/meetings/:mid` — single meeting.
- `DELETE /api/workspaces/:id/meetings/:mid` — cancel. ACL: organizer or admin. Calls `CalendarService.DeleteEvent`, sets `status = cancelled`.
- `GET /api/workspaces/:id/employees` — list employees (participant picker).

JSON is snake_case (consistent with the rest of the API).

## Domain logic

- **Name standard:** `[dept] | [type] | [host] | [YYYY-MM-DD] | [recurrence-label]`. For `once`, the recurrence segment is omitted. Generated by the backend; not user-editable.
- **Validation:** `ends_at > starts_at`; required fields (dept, type, host, date, start, end, recurrence); recurrence/type within known enums (with `Другое`/custom allowed for dept/type per ТЗ).

## Testing

- **Domain unit tests:** name generation (single + recurring), validation (end>start, required, enums).
- **Repository tests:** follow existing `postgres/helpers_test.go` pattern (insert/list/get/delete, workspace scoping, ACL filter).
- **Application/service test:** with the **stub** `CalendarService` — assert event "created" and meeting + participants persisted; delete cancels and calls `DeleteEvent`.

## Out of scope (later increments)

- Real Google Calendar/Meet adapter (service-account credentials, per-workspace config).
- Bot FSM registration (§3); Telegram notifications & reminders (§5).
- Recurrence **series expansion** (this increment stores frequency + creates a single event only).
- Conflict/overlap detection (§4.7); common free-slot checker (§4.8); employee schedule view (§4.6).
- Edit meeting (§4.4) and add/remove participants on existing meetings (§4.3) — creation includes initial participants only.
- CSV import of the employee directory (this increment: table + list endpoint + manual/seed population).
